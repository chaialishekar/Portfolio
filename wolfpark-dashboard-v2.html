Database Design — Case Study

WolfPark

A relational schema for NC State's campus parking problem — built around five real user needs, normalized through two rounds of revision, and backed by triggers and stored procedures rather than left as bare tables.

Course · EM589, Business Dynamics for Engineering Managers Team · Team S Stack · T-SQL (SQL Server)
01 — The problem

Not a shortage of spaces. A shortage of visibility.

Parking at NC State was unpredictable — not because the campus lacked spaces, but because nobody could see which ones were open before they arrived. That distinction shaped every table in this schema: the system needed to answer "where can I park right now, and am I allowed to?" for five very different people, in real time.

  • Time lost circling full lots before class or a shift
  • Faculty, staff, and contractors held different permits with no enforced boundaries
  • Campus events like basketball games routinely overflowed into multiple unrelated lots with no way to predict it

03 — Design decisions

Two anti-patterns, found and fixed

The first draft had two tables doing work they weren't built for. Both fixes came down to the same idea: a table can only hold one fact per cell.

1. Permit eligibility wasn't a list — it needed to be rows
Before — 1NF violation
ParkingLots
  PermitAllowed
    SET('S','Faculty','Staff', ...)
After — junction table
LotPermitTypes
  LotID       INT   (PK, FK)
  PermitType  VARCHAR(20)  (PK)

A multi-valued cell can't be indexed or joined — checking "can this student park here" meant a FIND_IN_SET() scan instead of a lookup. One row per lot-permit pair fixes that, and lets usp_AllocateSpace check eligibility with a plain join instead of string parsing.

2. One event, one lot — until a basketball game affects four
Before — models a lie
CampusEvents
  AffectedLotID
    INT  (single FK)
After — many-to-many
EventLotMap
  EventID  INT   (PK, FK)
  LotID    INT   (PK, FK)

A single foreign key can't represent a game overflowing into the Coliseum lot, Dan Allen Drive, the staff lot, and the parking garage at once. The alternative — repeating the event's name and time on one row per affected lot — just moves the same problem into the data instead of the schema.

05 — Enforcing the design

Rules live in the database, not just the app

One column is a deliberate exception to normal form: Availability.Status is derived from AvailableSpots, and recomputing it on every read would mean repeating the same CASE logic in every query. Instead, a trigger owns it — the value can only be written by the database, so it can't silently drift out of sync with the count it's based on.

trg_Availability_SetStatus — fires on every insert/update to Availability

UPDATE a
SET a.Status = CASE
    WHEN a.AvailableSpots <= 0 THEN 'Full'
    WHEN a.AvailableSpots < (pl.TotalCapacity * 0.15) THEN 'Limited'
    ELSE 'Open'
  END
FROM Availability a JOIN ParkingLots pl ON pl.LotID = a.LotID;

Allocating a space follows the same principle — eligibility and availability are checked inside a stored procedure, in a transaction, before anything is written:

usp_AllocateSpace — permit check, then availability check, then insert

IF @HasPermit = 0
  RAISERROR('Permit type %s not authorized for LotID %d.', 16, 1, @PermitType, @LotID);

IF @SpotsFree IS NULL OR @SpotsFree <= 0
  RAISERROR('LotID %d has no available spots.', 16, 1, @LotID);

INSERT INTO Allocations
  (UserID, LotID, VehicleID, AllocatedAt, ExpiresAt, Status)
VALUES
  (@UserID, @LotID, @VehicleID, GETDATE(),
   DATEADD(HOUR, @DurationHours, GETDATE()), 'Active');
